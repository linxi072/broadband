---

## 1. 功能定义（Functional Definition）

面向 **PC 运营后台** 的站内消息中心，承载各业务事件的统一通知能力：

- **事件源（生产者）**：订单支付成功、合约即将到期、宽带暂停/恢复、工单完工、SLA 超时赔付等。各模块在服务层调用 `NotificationService.notify(...)` 产生通知。
- **消费者（PC 后台）**：运营/管理员在「通知中心」查阅消息、按未读过滤、单条/全部已读；管理端可主动推送（如合约到期批量提醒）。
- **去重**：同一业务对象（eventType + refType + refId）在 24h 窗口内只推送一次，避免重复刷屏。
- **角色可见性**：通知标记目标角色（ADMIN / OPERATOR / ALL），列表按当前登录角色过滤（无法解析角色时回退展示全部）。

## 2. 接口契约（Interface Contract）

基址：`/api/admin/notification`，统一权限 `notification:view`（M240 目录 / M241 菜单，授权 ADMIN + OPERATOR）。

| 方法 | 路径 | 入参 | 响应 |
|---|---|---|---|
| GET | `/list` | `page`(默认1) `size`(默认20) `unreadOnly`(默认false) | `{list, total, page, size, unread}` |
| GET | `/unread-count` | — | `{count}` |
| POST | `/mark-read` | `{ids: string[]}` | `{ok, updated}` |
| POST | `/mark-all-read` | — | `{ok, updated}` |
| POST | `/create` | `{title, content, eventType?, refType?, refId?, targetRole?}` | `{ok, ids: string[]}` |

**服务层 API（供其他模块调用）**

```java
// 业务事件产生一条通知（去重命中返回 null）
String notify(String eventType, String title, String content,
              String refType, String refId, String targetRole);

// 管理端主动推送：targetRole=ALL 时按 ADMIN/OPERATOR 扇出为独立通知行
List<String> create(String title, String content, String eventType,
                    String refType, String refId, String targetRole);

// —— 事件语义封装（事件 → 通知内容映射，模板在方法内集中定义）——
String notifyContractExpiring(String contractId, String customerName, String packageName, String endDate, int daysLeft);
String notifyContractRenewed(String contractId, String customerName, String endDate, int months);
String notifyWorkOrderCompleted(String workOrderId, String customerName, String workerName, String completeTime);
String notifySlaPayout(String compId, String custName, String reason, double amount, String orderId);

// 实时推送汇聚接口（预留扩展点：WebSocket/SSE；未注入为 no-op）
public interface RealtimeSink {
    void push(String eventType, String title, String content, String refType, String refId, String targetRole);
}
```

**数据表 `notification`（第 46 张）**

| 列 | 类型 | 说明 |
|---|---|---|
| id | VARCHAR(32) PK | 通知ID（N + UUID 前缀） |
| event_type | VARCHAR(32) | 事件类型 |
| title / content | VARCHAR | 标题 / 正文 |
| ref_type / ref_id | VARCHAR(32) | 关联业务对象类型 / ID |
| target_role | VARCHAR(16) | ADMIN / OPERATOR / ALL |
| dedup_key | VARCHAR(128) | 去重键（含索引） |
| is_read | TINYINT(1) | 0 未读 / 1 已读 |

## 4. 核心逻辑与实现要点（Key Implementation Points）

1. **纯函数可测**：`buildDedupKey` / `resolveTargetRoles` / `render` 为静态纯函数，无 DB / 无 Spring 依赖，可直接单测（见 §5）。
2. **去重窗口**：`notify` 先 `SELECT COUNT(*) ... WHERE dedup_key = ? AND created_time >= ?`（窗口 24h），命中则跳过；保证「同一事件不重复打扰」。
3. **角色扇出**：`create` 对 `ALL` 调用 `resolveTargetRoles` 生成 `[ADMIN, OPERATOR]`，并对 refId 追加角色后缀使每行拥有独立 dedup_key，避免互相抵消。
4. **角色可见性**：列表/未读/已读按 `currentRole()`（取 authority `ROLE_ADMIN`/`ROLE_OPERATOR`，无法解析回退 `ALL`）过滤；`isRoleScoped` 统一判定。
5. **旁路容错**：业务模块调用通知用 try-catch 包裹，通知子系统异常不阻断核心业务。
6. **风格一致**：服务/控制器沿用 `@Autowired JdbcTemplate` + `LinkedHashMap` 响应 + 文本块 SQL + `str()` 辅助方法，与 `HouseholdController` / `AdminBroadbandController` 完全一致。

## 6. 事件源映射与处理流程

三类业务事件已接入 `notify` 通知模块（2026-10-08）。统一通过 `NotificationService` 的语义化方法产生通知，事件 → 通知内容的映射在 `NotificationService` 内集中定义，业务模块仅传入领域参数。

### 6.1 事件 → 通知内容映射表

| 事件 | eventType | 语义方法 | 标题模板（render） | 内容模板（render） | refType / refId | targetRole | 触发点 |
|---|---|---|---|---|---|---|---|
| 合约到期预警 | `CONTRACT_EXPIRING` | `notifyContractExpiring(contractId, customerName, packageName, endDate, daysLeft)` | `合约即将到期：{customerName}` | `客户 {customerName} 的「{packageName}」合约将于 {endDate} 到期（剩余 {daysLeft} 天），请及时跟进续约。` | `contract` / contractId | ALL | `POST /api/admin/contract/notify-expiring`（运营手动触发或定时任务） |
| 合约续约成功 | `CONTRACT_RENEWED` | `notifyContractRenewed(contractId, customerName, endDate, months)` | `合约已续约：{customerName}` | `客户 {customerName} 的合约已续约，期限顺延 {months} 个月，新到期日 {endDate}。` | `contract` / contractId | ALL | `AdminContractController.renew()` 续约落库后 |
| 工单完工 | `WORK_ORDER_COMPLETED` | `notifyWorkOrderCompleted(workOrderId, customerName, workerName, completeTime)` | `工单完工：{workOrderId}` | `工单 {workOrderId}（客户 {customerName}）由师傅 {workerName} 于 {completeTime} 完成施工。` | `workorder` / workOrderId | ALL | `WorkerController.complete()` 完工落库后 |
| SLA 赔付生成 | `SLA_PAYOUT` | `notifySlaPayout(compId, custName, reason, amount, orderId)` | `SLA 赔付生成：{compId}` | `客户 {custName} 触发 SLA 赔付：{reason}，赔付金额 ¥{amount}（关联订单 {orderId}）。` | `sla` / compId | ALL | `SlaServiceImpl.evaluate()` 生成赔付工单落库后 |

> 模板占位符由 `NotificationService.render(...)` 渲染；缺失占位符原样保留。
> 上述事件与「支付成功」`PAYMENT_SUCCESS`（见 §3 集成示例）共用同一 `notify` 写库 + 24h 去重机制。

### 6.2 处理流程

```
业务事件触发
   │  (e.g. 合约临期扫描 / 工单完工 / SLA 评估生成赔付)
   ▼
语义方法 notifyXxx(领域参数...)
   │  内部用 render(模板, 参数) 生成 title/content
   ▼
notifyEvent(eventType, title, content, refType, refId, role)
   ├─ notify(...)            → 24h 去重键查询
   │     ├─ 命中(窗口内已推送) → 返回 null（跳过，不写库、不推送）
   │     └─ 未命中           → INSERT 通知行，返回通知 id
   └─ publishRealtime(...)   → 仅在写库成功(id≠null)后调用
         └─ RealtimeSink?.push(...) 或 no-op（未注入时降级轮询）
```

- **去重**：`dedup_key = eventType|refType|refId`，24h 窗口内同一业务对象只通知一次（例如逐日扫描临期合约，每天提醒一次而不过度刷屏）。
- **容错**：所有接入点均为 `@Autowired(required=false) NotificationService` + try-catch 旁路，通知子系统异常不影响核心业务状态机。
- **可见性**：上述事件均 `targetRole=ALL`，PC 后台 ADMIN/OPERATOR 可见。

### 6.3 实时推送扩展点（WebSocket / SSE，后续增量 · 当前未实现）

实时推送**本期不实现**，但在设计中已预留清晰的扩展接口与钩子，启用时**业务模块零改动**：

- **接口**：`NotificationService.RealtimeSink { void push(String eventType, String title, String content, String refType, String refId, String targetRole); }`
- **钩子**：`NotificationService.publishRealtime(...)` 在每次事件写库成功后调用；若 Spring 注入了 `RealtimeSink` 实现则推送，否则 no-op（维持现有轮询拉取式：铃铛 60s 轮询 `/unread-count`）。
- **接入方式（未来）**：新增一个实现 `RealtimeSink` 的 Spring Bean（如 `WebSocketNotificationSink`，内部维护 `SimpMessagingTemplate` 或 SSE `SseEmitter` 注册表），按 `targetRole` 推送给在线客户端即可。所有 `notifyXxx` 语义方法已自动经此钩子，无需回改任何业务模块。
- **测试钩子**：`NotificationService.setRealtimeSink(...)`（包级可见）供单测注入模拟实现，验证事件已正确路由至实时通道（见 `NotificationServiceTest.realtimeRoutesToSink`）。
