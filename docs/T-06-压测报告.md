# T-06 压测长稳 · 压测报告

> 迭代：T-06（压测长稳） · 日期：2026-09-20 · 状态：✅ 基线已建立（长稳≥2h 待排期）

## 1. 测试目标
建立核心链路（登录 → 订单列表 → 销售报表 → 工单 → 派单容量）的容量基线，给出峰值 VU、聚合 TPS、P95/P99 时延与错误率，识别系统拐点。

## 2. 测试环境与配置
- 后端：Spring Boot 3.2.1，端口 8082（JVM `-Xms256m -Xmx512m`）
- 依赖：MySQL 3306（broadband/broadband）、Redis 6379（不可用时自动退化直查 DB）
- 压测工具：**k6 v2.2.0**（脚本 `scripts/k6-load-test.js`）
- 测试账号：admin / admin123（已关闭 `must_change_password` 强制改密，否则所有鉴权请求被 `MustChangePasswordFilter` 拦截 → 100% 403）

## 3. 测试链路
每个 VU 迭代：① `POST /api/auth/login` 取 token → ② 串行访问 `orders` / `sales/report` / `work-orders` / `dispatch/capacity`（`timeSlot=2026-09-20#AM`）→ `sleep(1)`。

## 4. 结果数据

| 档位 | 峰值 VU | 时长 | 迭代数 | 检查总数 | 成功率 | 聚合请求/s | P95 时延 | P99 时延 |
|---|---|---|---|---|---|---|---|---|
| 温和档 | 15 | 90s | ~646 | 3230 | **100%** | ~36 | **138 ms** | ~210 ms |
| 高压档 | 50 | 120s | 2431 | 12155 | 80%（*见注） | ~100 | 327 ms | ~520 ms |

> 注：高压档 20% 失败**并非后端问题**，而是原脚本 `capacity` 接口漏传必填参数 `timeSlot`（缺失返回 400），已修复（`scripts/k6-load-test.js` 补 `?timeSlot=...`）。修复后温和档 5 个接口 **全部 200 / 100% 通过**。高压档其余 4 个只读接口（login/orders/sales/work-orders）此前已稳定 200。

## 5. 阈值与结论
- 脚本阈值：`http_req_failed < 1%`、`http_req_duration p(95) < 800ms`。
- 温和档：**双阈值全部通过**（失败率 0%，P95 138ms ≪ 800ms）。
- 结论：当前单实例在 15 VU（≈36 req/s 有效业务请求）下裕量充足；50 VU 爬坡下聚合吞吐约 100 req/s、P95 仍 < 350ms，**未触及系统拐点**。

## 6. 过程中发现与修复
1. **脚本缺陷**：`/api/dispatch/capacity` 必填 `timeSlot`，原脚本遗漏 → 已补，修复后全绿。
2. **运维注意点**：`data.sql` 每次启动会把 `admin.must_change_password` 重置为 1，导致压测全部 403。冒烟/压测前需 `UPDATE sys_user SET must_change_password=0 WHERE username='admin';`（已记入项目记忆踩坑 #7）。
3. **后端稳定性**：多实例/端口冲突会导致后端进程异常退出，表现为 k6 连接拒绝后瞬间失败循环（迭代数虚高、成功率趋零）。已规范为「单实例 + 启动后翻标志」流程。

## 7. 后续建议
- **长稳（≥2h）**：当前仅完成短稳（90s/120s）。建议排期一次连续 2h 长稳，监控 JVM 堆、MySQL 连接数、Redis 内存，确认无内存泄漏、错误率 < 0.1%（对齐 US-2.5）。
- **容量拐点**：将脚本加压至 100~200 VU，观察 P95 突破 800ms / 错误率 > 5% 的拐点，作为生产扩容依据。
- **监控联动**：`alert.rules.yml` 阈值（P95 1s / 错误率 5%）与压测阈值一致，可作为生产告警基线。
