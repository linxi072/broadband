## 2. 技术选型

| 层 | 选型 | 说明 |
|----|------|------|
| 后端 | Spring Boot 3.2.1 / JDK 21（单体） | 单体应用，业务模块上限 5 个 |
| ORM | MyBatis-Plus（`mybatis-plus-spring-boot3-starter`） | 实体零注解，主键 `Ids.next()` 显式生成 |
| 安全 | Spring Security 6（`STATELESS`）+ 自研 HS256 JWT | 零三方安全依赖，授权每请求实时查库 |
| 前端（PC） | Vue 3.5 + Element Plus + Pinia + Vue Router + Vite 5 | 主题靛 `#4f46e5` |
| 前端（小程序） | 微信小程序（双独立工程） | 客户端蓝 `#2563eb` / 师傅端橙 `#ea580c` |
| 数据库 | MySQL 8.4 | 启动自动建表（幂等），不覆盖运行期数据 |
| 监控 | Actuator + Micrometer-Prometheus | 开放 `/actuator/prometheus` |
| 部署 | Nginx 反代 + systemd / 容器化 | `/api → :8082`，静态资源直出 |

**架构原则**：单体优先、模块收敛（后端业务模块上限 5）、配置原生（不引 Apollo/注册中心）、零三方安全依赖（自研 JWT）。

## 3. 模块划分与职责

### 3.1 后端模块（Spring Boot 单体）

| 模块 | 职责 | 关键能力 |
|------|------|----------|
| `community` | 小区覆盖、覆盖需求登记 | 覆盖查询、需求登记（C 端开放） |
| `install` | 智能派单 + 装维 SLA | 容量规则引擎、并查集聚类、贪心派单、SLA 时限/速率双评估、赔付 |
| `product` | 套餐/订单/客户/升级/流量/评价/发票 | 套餐升级引擎、流量查询、业务闭环、客户 360、营销看板、退款/发票 |
| `system` | RBAC / 平台聚合 / 字典配置 | 自研 JWT、用户/角色/菜单 CRUD、CSV、数据权限行级隔离、数据字典、参数配置 |
| `common` | 公共层 | Ids 生成、全局异常、统一响应 |

> 聚合类接口归入 `system` 的「平台聚合」（AdminPlatformController）与 `product` 的 `AdminProductController`，保持模块单向可拆。

### 3.2 关键技术决策

- **安全**：Spring Security 6（`STATELESS`）+ 自研 HS256 JWT（零三方依赖）；`JwtAuthFilter` 按 `dept` 建立 CUSTOMER / WORKER / ADMIN 身份。
- **权限同源**：21 权限码 / 5 角色 / 26 菜单，在「DB ↔ `@PreAuthorize` ↔ 前端 `meta.perm`」三处强制一致。
- **配置**：Spring Boot 原生（yml + 环境变量），多 profile（dev/prod），不引入 Apollo；规则参数以库内参数化 + 环境变量覆盖为准。
- **监控**：Actuator + Micrometer-Prometheus，开放 `/actuator/prometheus`。

### 3.3 分层与算法解耦

每个业务模块遵循「纯 Java 引擎（model + engine，可 `javac`+`java` 独立运行）+ Spring 适配层（Mapper / Service / Controller）」同构分层。核心算法保留 6 个可独立运行的 `*Demo`，无需 Maven / 数据库即可验证：

- `community.CommunityDemo`（可装性校验）
- `install.DispatchDemo`（容量规则 + 并查集聚类 + 贪心派单）
- `install.SlaDemo`（时限类 + 速率类评估与赔付）
- `product.PackageDemo`（融合套餐算价）
- `product.PackageUpgradeDemo`（升档补差 = 月差 × 合约剩余月数）
- `product.TrafficDemo`（流量阈值）

## 4. 前端架构

### 4.1 PC 管理后台（web-admin）

- 技术：Vue 3.5 + Element Plus（按需引入）+ Pinia + Vue Router + Vite 5。
- 规模：28 个 `.vue` 页面（23 条路由），主题靛 `#4f46e5`（CSS 变量收敛）。
- 导航：`navConfig` 驱动侧边栏，按 `user.perms` 过滤；路由守卫按 `to.meta.perm` 校验。
- 降级：后端不可达时页面降级内置「演示数据」并标 `SourceTag`。
- 详情类路由（如客户 360 `/customer/:id`）只加在 `router/index.js` 的 children，不进 `navConfig`，避免污染菜单。

### 4.2 微信小程序（双独立工程）

- 客户端 `broadband-miniapp/`：蓝 `#2563eb`，15 页（含登录）。
- 师傅端 `broadband-worker/`：橙 `#ea580c`，8 页，全接真实接口（含 401 门禁）。
- 登录态：手机号 + 验证码（演示 `1234`）→ `POST /api/auth/miniapp-login` 拿真实 token → `globalData` + Storage；`api.request()` 注入 Bearer。

## 5. 数据模型

共 **31 张表**（基线 25 张 + V1.11 退款/发票 + V1.13 字典/配置/报修扩展），分组如下：

| 域 | 代表表 |
|----|--------|
| 小区/覆盖 | `community`, `community_demand` |
| 装维 | `work_order`, `worker`, `worker_capacity`, `sla_rule`, `sla_record`, `compensation` |
| 订单/交易 | `biz_order`, `order_refund`, `invoice_apply` |
| 客户/套餐 | `customer`, `customer_contract`, `package_info`, `package_*`, `package_upgrade_order` |
| 评价 | `review`（含 `TO_EVALUATE` 状态） |
| 权限 | `sys_user`, `sys_role`, `sys_menu`, `sys_user_role`, `sys_role_menu`, `sys_department`, `sys_oper_log` |
| 字典/配置 | `sys_dict_type`, `sys_dict_data`, `sys_config`（V1.13 新增） |

> 表结构详见《数据结构说明书》。脚本 `schema.sql` 全部幂等（`CREATE TABLE IF NOT EXISTS` + `information_schema` 守卫补列），可安全重复执行。

## 6. 核心业务流程

### 6.1 业务主闭环

```
下单(PENDING) → 支付(PAID, 生成安装工单)
  → 智能派单(容量校验: 相邻3-4/非相邻1-2) → 师傅施工(INSTALLING)
  → 完工(DONE, 自动 SLA 评估 + 自动推送 TO_EVALUATE 待评价)
  → 客户评价(PENDING) → SLA 不达标自动赔付(compensation)
```

### 6.2 退款状态机（V1.11）

```
C端申请           财务审批
PENDING ──────► APPROVED ──────► REFUNDED（biz_order.status=REFUND）
   └─────────────────────────► REJECTED
```

### 6.3 电子发票（V1.11 占位）

```
C端申请(PENDING) ──► 财务开具(OPENED, 生成 invoice_no + pdf_url 占位)
                  └──► 驳回(REJECTED)
```

### 6.4 故障报修（V1.13）

```
C端申请(REPAIR) → 复用 dispatch 派单 + SLA 超时赔付 → 师傅完工 → 客户评价
  work_order.type=REPAIR, fault_category 关联字典, 进度时间线复用 sla_record
```

## 7. 非功能需求

### 7.1 维度方案

| 维度 | 方案 |
|------|------|
| 安全 | 自研 HS256 JWT；RBAC + 数据权限行级隔离；`sys_oper_log` 审计 |
| 性能 | 容量规则在内存聚类；k6 压测 20→50 VU，P95 < 800ms、失败率 < 1% |
| 可观测 | Actuator/Prometheus 指标 + 告警规则（时延/错误率/堆） |
| 可维护 | 单体模块上限 5；配置原生；CI/CD 构建+单测+镜像 |
| 兼容 | DB schema 仅追加列不删改，支持平滑升级 |

### 7.2 性能与安全指标

- **压测基线**：k6 由 20 VU 提升至 50 VU，P95 < 800ms，失败率 < 1%。
- **鉴权矩阵**（已实测）：无 token → 401、越权 → 403、授权内 → 200；登录失败 / 越权 / 写操作均落审计日志。
- **容量规则**：相邻小区 3–4 单、非相邻 1–2 单，超容自动拦截。
- **自检**：JWT 自研零三方依赖，配 7 条回归单测（`JwtUtilTest`）保障正确性。

## 8. 技术约束与演进

### 8.1 规划原则

1. **算法与框架解耦**：核心算法保持纯 Java 可独立验证，降低回归风险。
2. **接口先行、契约稳定**：REST 接口契约先定义，前后端并行开发。
3. **垂直切片交付**：按业务域逐模块打通「接口 → 前端 → DB」。
4. **基础设施按需后置**：DB / 安全按阶段接入；明确不引入的能力就不做半成品（不引入 Spring Cloud、不引入 Apollo）。

### 8.2 已知约束

- **微信支付**：当前 Mock 桩（`PayService` seam），真集成待商户号/APIv3 凭证。
- **师傅端验收**：8 页已接真实接口，待微信开发者工具真机视觉验收。
- **国际化**：暂未做 i18n。
- **配置动态刷新**：当前多 profile 静态切换，未做运行时热刷新。

### 8.3 风险与对策

| 风险 | 影响 | 对策 | 状态 |
|---|---|---|---|
| 设计稿规划页多、实现面广 | 进度压力 | 垂直切片，先打通核心链路再扩展 | 持续 |
| mock 与真实数据差异 | 联调返工 | 接口契约先行；已修复 2 处字段契约不一致 | 已缓解 |
| 容量 / SLA 规则需运营确认 | 业务正确性 | 规则参数化入库，先默认值后调优 | 持续 |
| 自研 JWT 的正确性 | 安全 | 零三方依赖换取可审计性，配 7 条回归单测 | 已落地 |
| 生产默认密钥/口令 | 安全 | `app.jwt.secret` 环境变量覆盖；首登强制改密 | 待办（上线前） |
