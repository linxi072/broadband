## 7. 本版修复的真实缺陷（可追溯）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 登录成功、token 完全正确，但**所有受保护接口一律 401** | `JwtUtil` 数字字面量扫描误写为 `"-+.0-9eE".indexOf(c)`，实际只放行字符 `0`/`9`，导致 `iat`/`exp` 解析失败；过滤器又**静默吞异常**，无任何日志 | 改为 `Character.isDigit` 判定的 `isNumberChar()`；过滤器 catch 补 WARN 日志；新增 7 条单测锁死行为 |
| 2 | `GET /api/admin/orders` 返回 500 | 联表 `biz_order o LEFT JOIN package_info pkg` 时 `SELECT id` 未加表别名 → `Column 'id' in field list is ambiguous` | 全部列加 `o.` 前缀（订单列表 + 看板最近订单两处） |
| 3 | `SlaEvaluation.summary` 输出 `[null]` | 主键在评估之后才生成，`describe()` 读到空 id | 主键改为在评估前生成 |
| 4 | 客户端「套餐列表」页**加载无数据** | `api.listPackages()` 请求 `/api/package/list`，但后端**无此端点** → 404 | 后端新增 `GET /api/package/list`（在售套餐 + 主图，开放层）；并补 `PackageMapper.selectOnShelfWithCover`（JOIN `package_image` MAIN） |
| 5 | 客户端「我的订单」页**空 / 被拦截** | `api.getOrders()` 请求 `/api/admin/orders`，该路径需 `order:view` 权限（越权 → 403），且语义是管理端全量订单 | 后端新增 `GET /api/order/my?customerId=`（按客户查自己的订单，开放层）；客户端改调此端点；订单列表已加入 `community_name` 字段 |
| 6 | 小程序登录**形同虚设** | `login()` 在本地直接返回一个假 token（`{token:'mock-...'}`），并未与后端交互，任何手机号都能登录 | 后端新增 `POST /api/auth/miniapp-login`（permitAll）：演示验证码 `1234` → 查客户 → 签发**真实 JWT**（dept=CUSTOMER）；两端 `login`/`workerLogin` 改调真实接口 |
| 7 | 任何接口**报错都被当成成功** | `utils/api.js` 的 `request()` 只在 `fail` 时 reject，`success` 回调里对 `statusCode>=400` 仍 `resolve`，导致 401/403/404 时页面静默无数据、难以排查 | `request()` 改为非 2xx 一律 `reject`（带 message），与后端统一错误结构对齐；两端同改 |

| 8 | 小程序**登录成功、token 完全正确，但所有受保护 C 端接口一律 401**（"能签发却用不了"） | `JwtAuthFilter` 只按 `sys_user` 表 `selectByUsername` 建认证；CUSTOMER 令牌的用户名不在后台用户表 → 返回 null → 不建 `Authentication` → 恒 401 | 过滤器按 `dept` 分支：CUSTOMER 直接建 `CustomerPrincipal` + `ROLE_CUSTOMER`，WORKER 建 `WorkerPrincipal` + `ROLE_WORKER` + `workorder:view` + `sla:view`；后台 SYS 路径保持不变 |
| 9 | 师傅端登录**形同虚设** | `workerLogin()` 本地直接返回假 token，未与后端交互 | 后端新增 `POST /api/auth/worker-login`（permitAll）：按 `worker.phone` 查表签发真实 WORKER 令牌；师傅端 `api.js` 改调真实端点 |

| 10 | 师傅端**能看到全部工单**（非本人范围） | 师傅端复用后台 `/api/admin/work-orders`，无 worker 维度过滤；且客户端可传 `?workerId=` 任意查看 | 新增 `GET /api/worker/work-orders` / `{id}`：服务端按 token 取 `workerId` 强制过滤，**忽略客户端传参**；越权详情返回空、越权完工返回 400 |
| 11 | 师傅端 4 个页面为**硬编码假数据** | 首页统计、容量看板、排班、完工确认均写死在 `data` 里，完工提交只是 `setTimeout` 假提示 | 新增 `GET /api/worker/summary`、`/capacity`、`/schedule`、`POST /api/worker/work-orders/{id}/complete`；4 页改调真实接口；`work_order` 增 `down_speed`/`up_speed`/`sign_name`/`service_items`/`complete_time` 五列并落库 |

> 第 1–3 条于 RBAC 阶段修复；第 4–7 条于 M8（小程序缺陷修复）修复；第 8–9 条于 M9（双端登录态收口）修复；第 10–11 条于 M10（师傅端数据绑定与隔离）修复。
> 第 7 条与第 1 条同源——**静默吞错**是系统性风险：后端过滤器曾静默吞 JWT 异常、前端 `request` 曾静默吞 HTTP 错误，二者都会把明确的失败伪装成「无数据」。
> 第 8 条与第 6 条同源——**"看起来完成了"的伪实现**：mock token 与真实令牌的差别，只有在真正打通鉴权链路时才会暴露。
