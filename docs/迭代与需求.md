- **三端工程**：微信小程序（客户端 20 页 / 师傅端 8 页）+ Vue3 PC 后台（33 个 `.vue` 页面）+ Spring Boot 3.2 后端（62 接口 / 25 表）。

### 3.2 v1.11 变更记录：退款 / 对账状态机（已交付 ✅）

**目标**：在业务订单生命周期中补齐「退款」状态，财务对账口径与实际资金流对齐。

| 编号 | 需求 | 验收标准 |
|------|------|----------|
| R1 | `biz_order.status` 新增 `REFUND` 终态 | schema 注释与枚举覆盖；历史库 ALTER 守卫补齐 |
| R2 | C 端 `POST /api/order/refund` 申请退款 | 仅 PAID/INSTALLING/DONE 可发起；幂等（同单已有 PENDING/REFUNDED 直接返回） |
| R3 | 后台 `GET /api/admin/refunds` 列表（finance:view） | 支持按 status 过滤；返回退款单 + 关联订单 + 金额 + 流水号 |
| R4 | 后台 `POST /api/admin/refunds/{id}/approve` | PENDING→REFUNDED，生成 `refund_no`，并将业务订单置 `REFUND`（营收扣减） |
| R5 | 后台 `POST /api/admin/refunds/{id}/reject` | PENDING→REJECTED |
| R6 | 财务对账口径对齐 | `finance/report`：revenue=PAID/INSTALLING/DONE；refund=REFUND（真退款）；cancelled=CANCELLED（取消不计营收）；营销汇总排除 REFUND |

**数据模型**

```sql
CREATE TABLE order_refund (
  id, order_id, order_no, customer_id, customer_name, amount,
  reason, channel, status,            -- PENDING/APPROVED/REJECTED/REFUNDED
  refund_no, operator, created_time, handled_time
);
```

**状态机**

```
C端申请           财务审批
PENDING ──────► APPROVED ──────► REFUNDED（同时 biz_order.status=REFUND）
   │
   └──────────────────────────► REJECTED
```

### 3.3 v1.11 变更记录：电子发票占位（已交付 ✅）

**目标**：提供电子发票的申请与开票流转闭环（占位实现，真实发票平台接入后仅替换 `pdf_url` 与开票动作）。

| 编号 | 需求 | 验收标准 |
|------|------|----------|
| I1 | C 端 `POST /api/invoice/apply` | 仅 DONE 订单可开；幂等；写入 `invoice_apply`(PENDING) |
| I2 | C 端 `GET /api/invoice/my` | 按客户名查询本人发票申请与状态 |
| I3 | 后台 `GET /api/admin/invoices` | 列表 + 按 status 过滤 |
| I4 | 后台 `POST /api/admin/invoices/{id}/open` | PENDING→OPENED，生成 `invoice_no` + 占位 `pdf_url` |
| I5 | 后台 `POST /api/admin/invoices/{id}/reject` | PENDING→REJECTED（记驳回原因） |

**状态机**：`PENDING → OPENED / REJECTED`，`pdf_url` 为占位地址，真实接入后回填。

### 3.4 v1.11 变更记录：师傅完工自动生成「服务评价」推送（评价闭环增强，已交付 ✅）

**目标**：师傅完工后系统自动向客户推送一条「待评价」，客户回填评分闭环评价。

| 编号 | 需求 | 验收标准 |
|------|------|----------|
| E1 | `WorkerController.complete()` 完工后 | 自动向 `review` 插入一条 `status=TO_EVALUATE` 记录（order_id=业务订单，customer/worker 名取自工单） |
| E2 | 幂等 | 同一订单已有 TO_EVALUATE 则不重复插入 |
| E3 | C 端 `POST /api/review/submit/{reviewId}` | 客户对 TO_EVALUATE 回填 score/tags/content → `status=PENDING`（进入原评价处理流） |

**闭环**：`完工(DONE)` → `系统推送 TO_EVALUATE` → `客户回填` → `PENDING（待客关/客服处理）`。

## 四、客户端小程序迭代需求

> 设计标杆：北京歌华有线电视网络股份有限公司《歌华有线》微信小程序 / 手机 App
> 适用范围：宽带业务管理系统 · 客户端微信小程序（`broadband-miniapp`）

### 4.1 背景与目标

客户端小程序当前已具备「首页 / 套餐 / 订单 / 我的」四大 Tab 与 20 个页面（含登录），并完成与后端真实接口的对接（CUSTOMER 令牌 + 演示登录 `1234`）。业务闭环（下单→支付→派单→装机→SLA 赔付→评价）与退款/发票占位已在 v1.11 落地。

但在**用户侧的「自助服务广度」与「运营留存能力」**上，与行业标杆《歌华有线》仍存在明显差距：歌华以「掌上营业厅」为定位，把宽带报装/续费/报修、账户余额/账单、积分商城、优惠活动、在线客服全部收敛到一个小程序内，实现「足不出户办业务」。本系统客户端目前「故障报修」仅为占位提示、缺少账户账单中心、积分与活动运营体系、在线客服，无法形成完整的用户自服务闭环。

**目标**：以歌华有线小程序为设计参考，补齐客户端核心自助短板（报修、账单、进度可视化），并引入运营留存能力（积分、活动、客服），使小程序从「下单工具」升级为「随身营业厅」。

### 4.2 标杆拆解：歌华有线小程序设计要点

| 维度 | 歌华有线做法 | 对我们的启示 |
|---|---|---|
| 信息架构 | 首页 / 分类 / 发现 / 我的 四大模块；首页布局 5G专区、宽带专区、充值、自助报装 快捷入口 | 现有 4 Tab 可保留；首页快捷办理应支持**高频入口智能推荐**，并新增「发现/活动」聚合运营内容 |
| 业务广度 | 宽带（报装/续费/暂停恢复/提速）、5G（选号开户/查询/密码变更）、有线（报装/授权刷新/暂停恢复）全部线上闭环 | 补齐**故障报修**、**宽带暂停/恢复**、**提速包**三类高频自助 |
| 故障报修 | 提交申请 → **实时查看受理进度/维修安排** | 报修须有完整表单 + 进度时间线，复用现有 `work_order` + 派单 + SLA 超时赔付 |
| 账户中心 | 充值后实时更新余额、**账单明细清晰可查**、多渠道支付 | 新增**账户与账单中心**（余额/账单/发票/充值记录），发票已在 V1.11 有占位需打通前端 |
| 积分体系 | 金币商城：每日签到/视频分享/邀请好友/问卷 → 积分兑换宽带时长、体验券 | 引入**积分成长体系**（签到/任务/商城），提升日活与续费转化 |
| 优惠运营 | 包月/包年/融合套餐、趸交优惠（买 N 送 N）、限时活动 | 新增**优惠活动专区**，首页促销由单行 note 升级为结构化活动流 |
| 在线客服 | 全天候在线客服，咨询 + 报修进度跟踪 | 新增**轻量在线客服/帮助中心**（FAQ + 工单式咨询） |
| 多账户 | 一个账号绑定多个家庭业务，多套住房统一管理 | 账单/工单按「住户」维度隔离，支持**多住宅切换** |
| 智能推荐 | 高频功能入口智能推荐、多数业务三步完成 | 首页快捷办理基于使用行为动态排序 |
| **设计教训** | 用户评测吐槽「点击选项后多出无意义确认页」 | 我方流程须**精简合并确认页**，避免冗余跳转 |

### 4.3 现状盘点（本系统客户端）

### 4.5 三阶段迭代计划

#### 阶段一 · V1.13 核心自助短板补齐（P0）

##### 5.1.1 故障报修全流程（替换现有 toast 占位）
- **前端**
  - 新增 `pages/repair/apply`（报修表单：故障类型[无法上网/网速慢/掉线/设备损坏]、描述、上传照片、关联地址/宽带账号、紧急程度）。
  - 新增 `pages/repair/list` + `pages/repair/detail`：工单列表与详情，含**进度时间线**（已受理→已派单→上门中→修复中→已完成）+ **SLA 倒计时/超时赔付提示**（复用 `/api/sla/board` 口径）。
  - 服务大厅「故障报修」入口改为跳转 `repair/apply`；首页快捷办理新增「故障报修」。
- **后端新增**
  - `POST /api/repair/apply`（生成 `work_order` type=REPAIR，写 `community` 派单容量校验后派单）。
  - `GET /api/repair/list`、`GET /api/repair/{id}`（含进度节点与 SLA 状态）。
  - 复用现有 `dispatch` + `sla` 模块，无需新建派单引擎。

##### 5.1.2 账户与账单中心
- **前端**
  - `我的` 页新增「账户余额 / 我的账单 / 我的发票」三入口；新增 `pages/account/account`（余额概览）、`pages/account/bills`（账单明细列表+筛选）、打通 V1.11 的 `pages/self/self` 发票申请/查看。
  - 账单明细展示：账期、费用项（宽带/融合/提速包）、金额、支付状态、关联订单。
- **后端新增**
  - `GET /api/account/summary`（余额/本月消费/合约到期日）。
  - `GET /api/account/bills`（按账期聚合，源 `biz_order` + 退款 + 发票）。
  - 发票：`POST /api/invoice/apply`、`GET /api/invoice/my` 已在 V1.11 提供，前端直接打通。

##### 5.1.3 订单/工单进度时间线统一化
- 安装、移机、报修三类工单在 `order/detail` 与 `repair/detail` 统一渲染**步骤进度条 + 当前节点预计时限 + SLA 倒计时**；超时自动显示「已触发赔付」标识。
- 复用 `work_order` 状态机与 `sla_record`，不新增表。

#### 阶段二 · V1.14 运营与留存（P1，参考歌华积分/活动）

##### 5.2.1 积分成长体系
- 新增 `pages/points/points`（首页签到、任务中心：完善资料/首评/邀请好友、积分明细）+ `pages/points/mall`（积分商城：兑换提速包/体验券/实物）。
- 后端 `points` 模块：`GET /api/points/balance`、`POST /api/points/sign`、`GET /api/points/tasks`、`GET /api/points/mall`、`POST /api/points/redeem`（兑换生成对应 `biz_order` 或优惠券）。

##### 5.2.2 优惠活动专区
- 新增「发现」Tab 或首页「活动」聚合卡：活动流（包年趸交买 N 送 N、限时新装赠礼、融合套餐折扣），活动详情 + 一键办理。
- 后端 `GET /api/promotions`（活动列表/详情），下单时校验活动优惠（接入 `PackageUpgradeEngine` 扩展）。

##### 5.2.3 在线客服 / 帮助中心
- 新增 `pages/support/support`：FAQ 分类检索 + 自助排障引导 + 工单式咨询（留言/回访）。
- 后端 `GET /api/support/faq`、`POST /api/support/ticket`；与报修/订单工单可互链。

#### 阶段三 · V2.0 智能化与多端（P2）

- **多住宅统一管理**：`address` 升级为「我的住户」，支持新增/切换住户，账单/工单/套餐按住户隔离（`sys_user`/账号下挂多 `dept` 或 `household_id`）。
- **高频入口智能推荐**：首页快捷办理基于用户行为（近 30 天办理类型）动态排序，提升三步办结率。
- **宽带自助：暂停/恢复**：新增 `POST /api/broadband/pause|resume`，前端 `self` 页提供开关（含暂停期间计费规则提示）。

### 4.6 非功能与一致性约束

- **主题与视觉**：客户端主色 `#2563eb` 维持不变；新增页面复用现有 CSS 变量与卡片/网格组件，保持与首页、服务大厅视觉一致。
- **鉴权与降级**：所有新接口沿用 CUSTOMER 令牌 + 401 门禁；后端不可达时页面降级内置「演示数据」并标 `SourceTag`（与 web-admin 一致规范）。
- **流程精简**：落实歌华教训——合并冗余确认页，报修/账单/活动关键路径控制在 3 步内。
- **演示登录**：保留 `1234` 验证码演示通道，新页面在演示态可走 mock 数据便于验收。
- **权限同源**：新增后端接口权限码纳入 RBAC 三处同源（DB↔`@PreAuthorize`↔前端 `meta.perm`）。

## 五、后续规划（V2.0 多住宅 / 智能推荐 / 暂停恢复）

### 5.1 多住宅统一管理
`address` 升级为「我的住户」，支持新增/切换住户，账单/工单/套餐按住户隔离（`sys_user`/账号下挂多 `dept` 或 `household_id`）。一个账号绑定多个家庭业务，多套住房统一管理，账单/工单按「住户」维度隔离。

### 5.2 高频入口智能推荐
首页快捷办理基于用户行为（近 30 天办理类型）动态排序，提升三步办结率；落实歌华「多数业务三步完成」的智能推荐理念。

### 5.3 宽带自助：暂停 / 恢复
新增 `POST /api/broadband/pause|resume`，前端 `self` 页提供开关（含暂停期间计费规则提示），对齐歌华「宽带有线暂停恢复」线上闭环能力。

### 5.4 V2.0 升级需求（规划表）

| 模块 | 需求 | 优先级 |
|------|------|--------|
| 体验 | 师傅端真机视觉验收（G5），输出多分辨率截图报告 | P0 |
| 后台 | 客户 360 / 套餐营销 / SLA 看板增强 | P1 |
| 交易 | 微信支付真集成（G4） | P1 |
| 运营 | 报表导出（Excel/PDF）、定时任务对账 | P2 |
| 多端 | i18n 框架 + 中英双语（G11） | P3 |
| 客户端 | 多住宅切换 / 智能推荐 / 暂停恢复 / 积分 / 活动 / 客服 | P2 |

### 5.5 模块约束（不变）

- 后端业务模块上限 **5 个**（当前 4：community / install / product / system）。新增聚合类接口归入 `system` 的「平台聚合」（`AdminPlatformController`），保持 4 模块单向可拆。
- 配置坚持 Spring Boot 原生（yml + 环境变量），不引入 Apollo。

### 5.6 风险与依赖

1. **后端新模块**：报修、账户账单、积分、活动、客服均需新增后端接口与（部分）表结构，建议与 V1.13/V1.14 后端迭代同步排期。
2. **微信支付真集成**：账户充值、积分商城兑换付费项依赖微信支付商户号/APIv3（当前 `PayService` 为 seam 占位），仍为阻塞项，需凭证后落地。
3. **数据口径**：账单聚合需统一 `biz_order`/退款/发票的口径（V1.11 `financeReport` 已对齐 REFUND 单列），避免重复计费展示。
4. **歌华设计教训复用**：避免为「演示完整性」引入多余确认页，保持流程精简。
